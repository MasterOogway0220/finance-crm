# Marketing WhatsApp Sender — Design Spec

> Status: **APPROVED 2026-07-03**, build starting. Extends the inactive-client outreach feature
> ([2026-06-17 spec](./2026-06-17-whatsapp-outreach-design.md), built on `@open-wa/wa-automate`).
> Stack: Next.js 16 App Router + React 19 + Prisma 6/MySQL + next-auth v5 + Tailwind/shadcn/sonner/zustand.
> App on Vercel; DB on Hostinger; office-PC worker/bridge runs open-wa.

---

## 1. Goal

Turn the admin-only "inactive outreach" tool into a general **Marketing WhatsApp Sender**:

1. A dedicated **Marketing login** (new `MARKETING` role) whose home is the WhatsApp page.
2. The sender **chooses recipients freely** — from the whole client book, from pasted/typed numbers, and (Phase 2) from the connected number's **WhatsApp groups** — not just a pre-computed "inactive" audience.
3. **Saved templates** so they pick a message instead of retyping.
4. (Phase 2) **Connect WhatsApp inside the app** — the web page shows the QR / phone-pairing code produced by the office-PC bridge and a live Connected status; sending is enabled only once linked.

**Ban-safety is unchanged:** all sends still flow through the DB queue and the office-hours daily-cap drip. "Connect, then it sends" means the bridge drains the queue at the safe rate — never an instant blast.

## 2. Hard constraint (why there is a bridge)

`@open-wa/wa-automate` drives a real headless-browser WhatsApp Web session and needs a **persistent Node process**. It **cannot** run on Vercel (stateless serverless). So the QR / pairing code is generated by the office-PC **bridge** (the evolved worker), which publishes its lifecycle to the **DB**; the web page reads that and renders it. The DB stays the only channel between Vercel and the office PC (no inbound network to the PC). Confirmed open-wa capabilities: QR via `ev.on('qr.**')` (base64 PNG), phone linking via `create({ linkCode: '<number>' })`, `getAllGroups()`, `getConnectionState()`.

## 3. Phasing

- **Phase 1 — pure app, ships first:** `MARKETING` role + login; recipient choice (all-clients + manual numbers); saved templates. No bridge changes required; works with the existing worker.
- **Phase 2 — bridge + in-app connect + groups:** `WhatsappSession` lifecycle, the Connect panel, and groups as a recipient type.

Each phase gets its own implementation plan. This spec covers both; Phase 1 is built first.

## 4. Roles & gating (Phase 1)

- Add `MARKETING` to the `Role` enum (`prisma/schema.prisma`). No new `Department` — the seeded marketing employee uses `Department.ADMIN`.
- New helper in `src/lib/roles.ts`:
  ```ts
  /** Can operate the WhatsApp sender: real admins plus the Marketing role (CA excluded). */
  export function canSendWhatsapp(role?: string | null): boolean {
    return isManager(role) || role === 'MARKETING'
  }
  ```
- Wire `MARKETING` into every role-aware spot (mirror the existing roles):
  - `ROLE_PRIORITY` (`roles.ts`) → `MARKETING: 2`.
  - `ROLE_LABELS` (`stores/active-role-store.ts`) → `MARKETING: 'Marketing'`; `getDashboardForRole` → `/whatsapp`.
  - `getNavItems` (`components/layout/sidebar.tsx`) → new `MARKETING_NAV = [ WhatsApp (/whatsapp), Clients — read-only (/masters/clients) ]`.
  - Login role-picker (`app/(auth)/login/page.tsx`) and topbar switcher (`components/layout/topbar.tsx`) already iterate the user's roles/labels — MARKETING flows through once labelled.
- **WhatsApp API routes + page:** swap the `isManager(role)` gate for `canSendWhatsapp(role)` in `audience` and `campaigns` routes and the new `templates` route; the page gate allows `['ADMIN','SUPER_ADMIN','MARKETING']` (active-role based, as already fixed).
- **Read-only client browse for MARKETING:** add `MARKETING` to the allowed-roles gate on the clients master page(s) (`masters/clients` and `masters/clients/mf`) and hide all edit / transfer / delete / import controls behind a **page-local** `viewerReadOnly = isReadOnly(role) || role === 'MARKETING'`. **Do NOT** add `MARKETING` to the global `isReadOnly` / `shouldBlockMutation` boundary (`roles.ts` + `proxy.ts`) — that global read-only block would reject Marketing's own WhatsApp write endpoints (queue campaign, manage templates), breaking the feature. The client mutation APIs already reject non-managers, so hiding controls is clean UX + defense-in-depth, not the security boundary.

- Seed a marketing login (mirror `prisma/seed-test-users.ts` upsert): `role: MARKETING`, `department: ADMIN`, designation `'Marketing'`. Real credentials set by the owner; a `*@test.local` entry is added to the test seed for local testing.

## 5. Recipient choice (Phase 1)

Three sources feed one selection; the campaign is the union, deduped by normalized phone.

**a) Clients — all (not just inactive).** Extend `GET /api/whatsapp/audience` with `scope=inactive|all` (default `inactive` for back-compat):
- `scope=all` builds the set from **all** clients (both departments), deduped by phone (equity preferred), invalid phones dropped — reusing `dedupeAudienceByPhone`. `segment` still applies under `scope=inactive`. Marketing UI defaults to `scope=all`.
- Keep `search`, pagination-after-dedupe, `idsOnly`, and the new stable `orderBy`.

**b) Manual numbers.** A textarea: one recipient per line, `number` or `number,Name`. Parsed client-side into `{phone, name?}`, validated with `normalizeWhatsappPhone`; invalid lines flagged inline.

**c) `POST /api/whatsapp/campaigns` accepts a union.** Body becomes `{ clientIds?: string[], manualRecipients?: {phone: string, name?: string}[], message: string }` (at least one recipient required). Build rows from both; dedupe across the whole set by normalized phone; `clientId` null for manual rows; `clientCode = 'MANUAL'`; `clientName` = the provided name or the number itself. Response keeps `{ campaignId, queued, skippedInvalid, skippedDuplicate, skippedMissing }`.

## 6. Templates (Phase 1)

- New model:
  ```prisma
  model WhatsappTemplate {
    id          String   @id @default(cuid())
    name        String
    body        String   @db.Text
    createdById String
    createdAt   DateTime @default(now())
    updatedAt   DateTime @updatedAt
    @@index([createdById])
  }
  ```
  **Shared** across all senders (no per-user scoping).
- `src/app/api/whatsapp/templates/route.ts`: `GET` (list, newest first), `POST` (create `{name, body}`). `src/app/api/whatsapp/templates/[id]/route.ts`: `PATCH` (edit), `DELETE`. All gated by `canSendWhatsapp`; zod-validated; `logActivity(module:'WHATSAPP')`.
- Page: a **Templates** control — a `<Select>` to load a template into the compose box, a "Save current as template" action (name prompt), and a small manage/delete affordance. `{{name}}` personalization unchanged (works for client rows and manual rows that carry a name).

## 7. Phase 2 — bridge, connect panel, groups

**Data model:**
```prisma
enum WhatsappSessionState { DISCONNECTED CONNECTING QR PAIRING CONNECTED }
enum WhatsappTargetType   { CONTACT GROUP }

model WhatsappSession {           // singleton row (id = "default")
  id             String   @id @default("default")
  state          WhatsappSessionState @default(DISCONNECTED)
  qr             String?  @db.Text   // base64 PNG data URL, when state=QR
  linkCode       String?             // pairing code, when state=PAIRING
  requestedPhone String?             // web writes this to request phone-linking; bridge consumes
  groupsJson     String?  @db.Text   // cached getAllGroups() [{id,title,canSend}]
  updatedAt      DateTime @updatedAt
}
// WhatsappMessage gains:
//   targetType WhatsappTargetType @default(CONTACT)
//   targetId   String?            // resolved chat id (91xxxx@c.us or xxxx@g.us); null → derive from phone
```

**Bridge (evolve `worker/send.js`):**
- On boot, upsert `WhatsappSession`; register `ev.on('qr.**')` → write `state=QR, qr=<base64>`; poll `getConnectionState()` → write state; on `CONNECTED` write `state=CONNECTED` and refresh `groupsJson` from `getAllGroups()`.
- Poll `requestedPhone`: when set, (re)start with `create({ linkCode: requestedPhone })`, write `state=PAIRING, linkCode=<code>`, clear `requestedPhone`.
- Send loop unchanged except: target = `targetId ?? \`${normalizeWhatsappPhone(phone)}@c.us\``; keep the connection-guard/daily-cap/window logic already in place.

**API (Phase 2):**
- `GET /api/whatsapp/session` → `{ state, qr, linkCode, groups }` (from the row). `POST /api/whatsapp/session/link` `{ phone }` → sets `requestedPhone`. Both `canSendWhatsapp`-gated.
- `campaigns POST` extends recipients with `groupIds?: string[]` → rows with `targetType=GROUP, targetId=<@g.us>, clientName=<group title>`.

**Frontend (Phase 2):** a **Connect** card polling `GET /session` (~3s): shows Connected ✓ / status; when not connected, renders the QR image and a "Link with phone number" input (posts `/session/link`, then shows the returned code). The **Queue Campaign** button is disabled unless `state==='CONNECTED'`. A **Groups** recipient source lists `groups` (title, id) with checkboxes.

## 8. Build order

**Phase 1 plan:** (1) `MARKETING` role + `canSendWhatsapp` + all role wiring + seed; (2) `audience` `scope=all`; (3) `campaigns` manual recipients; (4) `WhatsappTemplate` model + templates API; (5) page: recipient sources (all-clients + manual) + templates UI; (6) verify (`tsc`, `vitest`, `eslint`). `prisma db push` deferred (owner-approved) — adds the `MARKETING` enum value + `WhatsappTemplate` table.

**Phase 2 plan (separate):** session model + bridge lifecycle + connect panel + groups + `targetType/targetId`.

## 9. Testing

- Unit (vitest, pure logic): manual-recipient line parser (`parseManualRecipients`), union-dedupe (extend/verify `dedupeAudienceByPhone` usage), template body validation. Reuse `normalizeWhatsappPhone` tests.
- Type/lint gates: `npx tsc --noEmit` clean; `npm test` green; `eslint` on touched files. Worker stays `eslint`/`tsc`-excluded.

## 10. Deferred deploy steps (owner-approved, not run by build)
- `npx prisma db push` — adds `MARKETING`, `WhatsappTemplate` (Phase 1) and `WhatsappSession`/enums/`WhatsappMessage` columns (Phase 2).
- Create the real Marketing login (set password); office-PC bridge run + QR/pairing scan (Phase 2).
